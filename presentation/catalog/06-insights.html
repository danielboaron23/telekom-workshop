Run 02 · Insights · what the second run taught us

Redesigning is
harder than designing.

Run 1 had nothing to argue with — a screen that didn't exist can't be defended. Run 2 had a finished, pixel-matched, test-covered screen, and the work was mostly about proving what was wrong with it before touching it, then not breaking it on the way past.

Same three skills. Same order. The differences that mattered were evidence, a sibling route, and a second direction to argue against.

Conclusions from the redesign · every choice, and what forced it

Why /catalog-v2 looks the way it does

We put the customer on the catalogCustomer strip: name, real address, holdings, current line
Because the failure wasn't cosmetic — the screen was wrong about the customer, showing Seattle for a Singapore account. And because the agent otherwise holds the 360 in their head while someone talks to them. 4 screens across Navan, Deel and HubSpot name the other person before the catalog is usable at all.
We made the current plan a card in the gridChipped Current, primary action disabled
Because “which is better than what they have?” is the actual question on a call, and it can't be answered from four identical tiles. 5 of 5 plan pickers in the sample put current on the same surface as available — and Bonsai in particular disables the action rather than hiding the row, which keeps the comparison honest.
We wired search and printed the real count“6 offers”, and six cards
Because a control that looks live and isn't costs more trust than a missing control. “100 Results” over 8 cards teaches the agent to distrust every number on the screen. Faire, Stripe and Salesforce all print the count of rows they actually have — Salesforce even names the filters causing a zero.
We made Details a panel, not a pageGrid stays; × / overlay / Escape close it
Because navigating away loses the other offers the agent was mid-comparison on. Deel keeps a 19-item list visible and does the detail work in a right panel. Zendesk's compare-table modal was the tempting alternative and was rejected: that's a vendor selling its own SKUs to an admin, not an agent configuring an offer for someone else.
We refused to build eligibilityNo greyed-out offers, no rules
Because 0 of 16 references showed a catalog hiding or greying an offer because a rule fired — a screenshot can't show a rule. Building it would have meant inventing a rules engine and calling it a design decision. The omission got written into the PRD as a non-goal, so the next run inherits a known gap instead of a surprise.

One thing worth keeping from each stage

What transfers to the next run

stage 01 · the problem

Read the code before you judge the pixels

The Figma-matched screen was fine. Six of its controls had no handlers and its headline number was a hardcoded lie — none of which is visible in a screenshot or a review. The audit was rg, not taste.

stage 01 · the skills

A retro that changes no file is decoration

Run 1 found the prompts were missing parameters. Run 2 started by editing both skill files — tools and a definition of done for the PM, triggers and a review gate for the researcher. The researcher then fired on a landed brief without being asked.

stage 02 · research

The most useful finding was a zero

0 of 16 screens showed eligibility. Counting made the absence sayable — and a counted absence is what lets you cut scope on evidence rather than on time pressure. “Most catalogs do X” only becomes an argument once you know what X costs.

stage 03 · the spec

Name the command, not the confidence

Seven criteria, each with the command that proves it. The one that mattered most asserted that the screen we weren't building still worked — and it's why /catalog can still be demoed, lies intact, beside its own replacement.

stage 04 · the build

A sibling route beats a brave migration

Three catalogs, one repo, zero regressions, and a comparison you can put on a slide. Rebuilding in place would have made every design argument a risk conversation.

comparison · two directions

Build the control group

The off-system version isn't shipping — it converted “the design system feels dated” into three specific requests (photos, ratings, a cart) each with a running example behind it.

The parts that didn't go well

Four things that cost us time

Two rejected designs

“Off the design system” was read as “make it pretty”

An editorial magazine layout, then a dark compare-switchboard — both rejected before the marketplace landed. Nobody had written down what off-system was for, so the first two attempts optimised for looking impressive.

Fix: give the off-system probe its own one-line brief — “what would a product company ship?” — before the first pixel.
Skipped gate

The PRD went straight to build

Checkpoint 3 was skipped on a “go now”. The spec held up — but nobody had read the cut before code existed, and the one weak part of it (a single entry point) only surfaced later, in the spec's own weak-section paragraph.

Fix: the cheapest gate in the chain is the one right before code. Keep that one.
Self-inflicted bugs

Two React mistakes in the off-system build

State initialised from a variable declared later in the component, and a hydration mismatch from reading search params. Both caught in the browser, not in review — a screen that renders can still be wrong before it settles.

Fix: open every new route in a real browser before saying it's done. tsc did not catch either one.
Known gap, shipped

Almost nobody can find the new screen

Six things link to /catalog; only Products → Add new reaches /catalog-v2. Four of those links are asserted in the flow test, so repointing them is a product call, not a refactor.

Fix: it's written into the PRD as the weak section, with the reason. The next run starts from a known problem.

What came out of it

Six documents and two screens

A research brief, 16 captured references with per-screen notes, a findings write-up, a 10-slide research deck, a PRD and a screen spec — then /catalog-v2 (5 components, 12 offers, Storybook stories) and /catalog-studio.

Every claim in this deck points at a file or a command in the repo.

The one sentence version

The screen wasn't unfinished — it was for the wrong person

Dead controls were the symptom. The cause was a consumer storefront handed to a professional working on someone else's behalf, with a customer waiting on the line.

Every choice in /catalog-v2 follows from fixing that one thing.

Run 02 · close

Anyone can rebuild a screen. The work is proving it needed rebuilding.

Three things to steal from this run: audit the code, not the mockup · count your references so an absence can be an argument · build the second direction you don't intend to ship, because it's the only way to make a design system conversation concrete.

And keep the gate before code. It's the cheapest one in the chain and it's the one we skipped — the only part of this deck with an apology in it.
