One insight per stage

The five things that actually mattered

1 Skillsthe setup A skill is only worth having if it knows your product. The generic version says "write clear requirements"; ours knows there's no error colour token and that duplicate Figma frames are states, not screens.
2 Building themthe method The research skill got good because the agent tested the pipeline before designing it — one API call, one curl, one read of the existing decks. Each experiment changed the design.
3 Researchthe evidence Research earns its keep when it argues with the pattern. Seventeen references agreed on one required field and a modal; we took the speed and rejected both.
4 Specthe plan Research decides what to build; the codebase decides whether it's buildable. Three decisions changed after reading real files — including a 404 that would have shipped.
5 Designthe build Specs are checked by reading; designs are checked by rendering them and looking. Three bugs only existed once something was running.

The rule that made the whole run safe

"after each of the skill finish you let me verfing all"

That clause — typos and all — is the most important thing I typed all day. Three checkpoints, and each one caught something:

Checkpoint 1 · after research
Confirmed the argument, not the screenshots
The research recommended rejecting the majority pattern twice. That needs a human yes before it becomes a spec — otherwise you've automated a strong opinion nobody agreed to.
Checkpoint 2 · after the PRD
Approving the destination exposed a 404
Because I approved "land on the Customer 360", the PM then had to check whether it was buildable — and it wasn't. The checkpoint is what forced the check.
Checkpoint 3 · after the design
Caught a mislabelled state
A screenshot captioned as the ID block was actually the name-match warning. 90 out of 90 tests passed either way.

Three skills running unattended would have produced the same four files — and shipped a 404, an invented component, and a mislabelled state. The checkpoints are the difference between delegation and abdication.

The honest slide

Green tests are not the same as a correct screen

Everything below passed some form of automated check while still being wrong. This is the argument for staying in the loop:

  • 1A 404 that would have shipped — the approved success destination was unreachable in a static build. No test existed for a route nobody had written yet.
  • 2An invented component that already existed. The research called the duplicate banner "genuinely new"; two files in the repo already did it.
  • 3Two servers reporting an older truth — 44 stories and 404s on real routes. A green run against a stale process is worse than no run.
  • 4A screenshot labelled as the wrong state. Tests green, caption wrong. Only looking at the image caught it.

Every stage was logged as it happened into workshop/WORKFLOW_LOG.md — the prompt, what came back, what broke, and the one-line takeaway.

This deck was generated from that log, not reconstructed from memory afterwards. That's why it still contains the failures — the stale server, the wrong focus selector, the mislabelled screenshot. Write the log while you work and the retro writes itself; write it afterwards and you'll only remember the parts that went well.

The one thing to remember

Give the machine a standard, then make it show you its work.

The skills carry the standard — read the repo, tag every element, name your weak sections, lead with the answer. The checkpoints make it show the work. Neither one is optional, and neither one is about the model you're using.
